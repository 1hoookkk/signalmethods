# X3 Binary Contract

The authoritative description of every X3 filter file family, its binary
layout, and its role in the pipeline. Everything below is traced to a
specific DLL address, Ghidra extract, or byte-comparison proof.

---

## 1. File families

### 1.1 ROM tables — `ref/x3_menu/raw_tables/*.raw`

Verbatim byte ranges extracted from `EmulatorX.dll` at known addresses.
Each table is the **writer input**: a lookup table indexed by MORPH, Q,
and sample-rate family.

These are **not** runtime coefficients. They are consumed by the per-class
writer functions which transform them into packed corner words.

| File | DLL address | Bytes | Rate stride | Rates | Stages |
|---|---|---|---|---|---|
| `lp.raw` | `0x1806d65e0` | 160 | 40 | 4 | 1 |
| `hp.raw` | `0x1806d6680` | 160 | 40 | 4 | 1 |
| `swept_eq_1.raw` | `0x1806d6720` | 160 | 40 | 4 | 1 |
| `swept_eq_2.raw` | `0x1806d67c0` | 160 | 40 | 4 | 1 |
| `swept_eq_3.raw` | `0x1806d6860` | 160 | 40 | 4 | 1 |
| `bandpass.raw` | `0x1806d6900` | 160 | 40 | 4 | 1 |
| `contrary_bandpass.raw` | `0x1806d69a0` | 160 | 40 | 4 | 1 |
| `phaser_1.raw` | `0x1806d6a40` | 320 | 80 | 4 | 2 |
| `phaser_2.raw` | `0x1806d6b80` | 320 | 80 | 4 | 2 |
| `bat_phaser.raw` | `0x1806d6cc0` | 320 | 80 | 4 | 2 |
| `flanger_lite.raw` | `0x1806d6e00` | 480 | 120 | 4 | 3 |
| `vocal_ah_ay_ee.raw` | `0x1806d6fe0` | 480 | 120 | 4 | 3 |
| `vocal_oo_ah.raw` | `0x1806d71c0` | 480 | 120 | 4 | 3 |

**Evidence for table identity**: byte-comparison of `lp.raw` offset 0–39
against `2_pole_lowpass_44100.raw` offset 0–39 — identical. The runtime
block for 1-stage filters is a verbatim copy of the ROM table's per-rate
segment (see §1.2).

### 1.2 Runtime blocks — `ref/x3_menu/runtime_blocks/*.raw`

**Writer output**: the packed corner words produced by each class writer,
organised as 4 corners × N stages × 5 u16 words, little-endian.

Generated by the (missing) extraction script `tools/extract_x3_menu_filters.py`
— referenced in the manifest and README but not present in this repository.

**Binary layout per file**:

```text
[corner 0] [corner 1] [corner 2] [corner 3]

Each corner = N stages × 5 u16 words × 2 bytes

Corner order: (M0,Q0), (M100,Q0), (M0,Q100), (M100,Q100)
  — matches body240 corner order exactly
```

| output_stages | bytes per file | files |
|---|---|---|
| 1 | 40 | LP 2-pole, HP 2-pole, BP 2-pole, Contrary BP, Swept EQ 1/2/3 |
| 2 | 80 | LP 4-pole, HP 4-pole, BP 4-pole, Phaser 1/2, Bat Phaser |
| 3 | 120 | LP 6-pole, Flanger Lite, Vocal Ah-Ay-Ee, Vocal Oo-Ah |

68 files total (17 filters × 4 sample rates).

**Evidence for content**:

1. `2_pole_lowpass_44100.raw` (40 bytes) ≡ `lp.raw` bytes 0–39 (the
   44100 Hz segment). Byte-identical. The writer for 1-stage filters is
   a passthrough — it copies the ROM table row directly.

2. `4_pole_lowpass_44100.raw` (80 bytes) ≡ each corner's ROM table row
   duplicated twice. The writer for N-stage simple filters replicates
   the prototype stage N times.

3. `6_pole_lowpass_44100.raw` (120 bytes) ≡ each corner's ROM table row
   triplicated.

4. `vocal_ah_ay_ee_44100.raw` (120 bytes) — 3 genuinely distinct stage
   rows per corner (different words: `fcd0 fdff fca5 fc80 0c88` /
   `fcdf fdff fc7f fc80 0c88` / `fcdf fdff fc64 fc80 0c88`).
   The ROM table stores distinct stages; the writer preserves them.

`morph_designer_base` both `8eafb7f3...`).

### 1.4 Existing converted bodies

**X3F_*.body240** (in `bodies/candidates/`, generated by
`tools/x3_fundamentals_to_bodies.py`):

- 17 bodies, one per fixed-class filter
- Source: 44100 Hz runtime blocks only
- Identity-padded to 6 stages
- Certified through TRENCH's `certify()` at 44100 Hz
- Codec equivalence verified against df2 `packed_interp` reference decode
  (worst-case difference < 0.01 dB at corners)

**x3_shape_*.body240** (in `plugin/presets/bodies/` and `presets_ship_v1/bodies/`):

- ~105 Morph Designer presets (names like "Crispy", "Buzzy", "Wah Wah")
- Generated from Emulator X XML template data through the Morph Designer
  compiler grammar (types 1–3, documented in
  `ref/ghidra_extracts/morphdesigner_types.md`)
- Separate pipeline from the fixed-class ROM table filters
- NOT in scope for the runtime preset import workflow

**X3_*.body240** (in `bodies/candidates/`, from capture rig):

- Measurement-derived: `capture_x3.py` → audio recording →
  `corners_from_wavs.py` → ARMA fitting
- These are CAPTURED MEASUREMENTS, not runtime presets
- Must never be confused with byte-extracted runtime preset imports

## 2. Word encoding

### 2.1 The codec is minifloat, not fixed-point

**The README at `ref/x3_menu/README.md` states**: "The runtime blocks are
raw fixed-point coefficient words."

**This is contradicted by multiple independent lines of evidence**:

1. **Ghidra decode function** (`FUN_1802c3600`, documented in
   `ref/ghidra_extracts/runtime_hacks.md`):
   ```text
   decode(0x0000) = 0.0
   decode(0xffff) = 1.0
   ```
   This is the sentinel behaviour of TRENCH's minifloat `decode()`, not
   fixed-point Q15/Q14 division.

2. **Recombination formula matches TRENCH exactly**:
   ```text
   c0 = 4 * d0 + d1     (Ghidra)
   c0 = 4 * d0 + d1     (TRENCH stage_words_to_kernel, COMBINE_K = 4.0)
   c1 = d1
   c2 = 4 * d2 + d3
   c3 = d3
   c4 = runtime_scale * d4   where runtime_scale = 4.0
   ```

3. **Codec equivalence test passes**: `x3_fundamentals_to_bodies.py`
   decodes each runtime block corner through df2's minifloat path,
   encodes through TRENCH's path, and probes both — worst-case
   difference < 0.01 dB across all 17 filters.

4. **Pad sentinel is a minifloat sentence, not a fixed-point one**:
   `[0xdfff, 0xffff, 0xdfff, 0xffff, 0xe000]` — these values are
   meaningful in minifloat (near-zero, 1.0, near-zero, 1.0, gain
   encoding) but arbitrary in Q15.

**Conclusion**: The ROM tables, runtime blocks, and all X3 packed
coefficient words use the same minifloat codec as the P2K `.body240`
format. The "fixed-point" label in the README is incorrect.

### 2.2 Decode chain

```text
u16 words (minifloat)
  → decode(word) → f64 ∈ [0, 1]
  → recombine: [4*d0+d1, d1, 4*d2+d3, d3, 4*d4]  (kernel space)
  → kernel_to_biquad: [(c0-2)*c4, (1-c1)*c4, c2-2, 1-c3, c4]  (biquad space)
  → cascade
```

This chain is identical for P2K bodies and X3 runtime blocks. The
difference is only in how the u16 words were authored, not in how they
are consumed.

## 3. Structure classification

| Structure | Classification | Evidence |
|---|---|---|
| `raw_tables/lp.raw` etc. | **Raw lookup table** | Consumed by writer functions (e.g. `FUN_1802c4b80`); byte-identical to runtime block rows; stored in DLL `.rdata` |
| `raw_tables/morph_*.raw` | **Writer input** | Parameter tables for generated-class writers; consumed at compile time, not at runtime |
| `runtime_blocks/*.raw` | **Writer output = preset state** | The packed corner words as written by each class writer; these are the snapshot of what the writer produces at the four corners |
| `X3F_*.body240` | **Writer output → body240** | Verbatim runtime block words packed into body240 format, identity-padded to 6 stages |
| `x3_shape_*.body240` | **Preset state** | Morph Designer user presets compiled through the type 1–3 grammar |
| `X3_*.body240` (capture) | **Measurement-derived** | Audio captures fitted through ARMA; NOT runtime presets |
| `morph_designer_bypass.raw` | **Pad sentinel** | The identity row `[0xdfff, 0xffff, 0xdfff, 0xffff, 0xe000]` used to pad inactive stages |

## 4. Corner order confirmation

The manifest declares corners as `["M0_Q0", "M100_Q0", "M0_Q100", "M100_Q100"]`.

Confirmed by:
- `x3_fundamentals_to_bodies.py` line 9: "Corner order in the blocks is
  MORPH0/RES0, M100/R0, M0/R100, M100/R100 — the body240 corner order
  with RES as the Q axis"
- Body240 spec (CLAUDE.md): corner order (M0,Q0), (M100,Q0), (M0,Q100), (M100,Q100)
- Both match; no transposition needed

## 5. Identity padding

Stages beyond `output_stages` are padded with the sentinel row:
`[0xdfff, 0xffff, 0xdfff, 0xffff, 0xe000]`

This is the same pad used by Morph Designer (`DAT_1806d7500`) and by
TRENCH's body240 format. When decoded through `kernel_to_biquad`, this
row produces an exact unity biquad `[1, 0, 0, 0, 0]` — electrically
invisible in the cascade.

Proven by:
- `x3_fundamentals_to_bodies.py` line 50: `identity_row()` encodes
  `(1000, 0, 1000, 0, 1.0)` which produces these exact words
- `engine_null.py` line 25: `PAD = (0xdfff, 0xffff, 0xdfff, 0xffff, 0xe000)`
- `verify_pipeline.py` C3: all-sentinel body flat to < 0.5 dB

## 6. Writer duplication law

For simple filter classes (LP, HP, BP, Swept EQ): the writer replicates
a single prototype stage N times to achieve the advertised pole count.

Proven by byte comparison:

```text
lp.raw[0:10]   = fcdf fdff ed11 fcac ef11   (corner 0, prototype stage)
2_pole_44100   = fcdf fdff ed11 fcac ef11   (corner 0, stage 0 — same)
4_pole_44100   = fcdf fdff ed11 fcac ef11   (corner 0, stage 0 — same)
                  fcdf fdff ed11 fcac ef11   (corner 0, stage 1 — same)
6_pole_44100   = fcdf fdff ed11 fcac ef11   (corner 0, stages 0/1/2 — all same)
```

For complex classes (Vocals, Flanger): the ROM table stores genuinely
distinct stage designs. The writer preserves them without duplication.

```text
vocal_ah_ay_ee corner 0:
  stage 0: fcd0 fdff fca5 fc80 0c88  (distinct)
  stage 1: fcdf fdff fc7f fc80 0c88  (distinct)
  stage 2: fcdf fdff fc64 fc80 0c88  (distinct)
```
