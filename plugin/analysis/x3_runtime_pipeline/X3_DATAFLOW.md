# X3 Dataflow: preset selection → live filter coefficients

The complete path from menu click to samples in the DAC. Every arrow is
traced to a Ghidra function address, a byte-comparison proof, or a DLL
address in `EmulatorX.dll` (SHA256
`32b08c9bbe19c97cdbf11493576fc09231b1ebb9770d85330f5fa9948db7bf07`).

---

## 1. Architecture overview

The X3 filter engine has three layers:

```
┌─────────────────────────────────────────────┐
│  LAYER 1: AUTHORING (compile time)          │
│  Writer functions produce corner banks from │
│  ROM tables + control parameters            │
├─────────────────────────────────────────────┤
│  LAYER 2: INTERPOLATION (per-note or        │
│  per-block)                                 │
│  Bilinear interpolation of packed u16 words │
│  between the four corners                   │
├─────────────────────────────────────────────┤
│  LAYER 3: DECODE + DSP (per-sample)         │
│  Minifloat decode → kernel → biquad →       │
│  cascade → AGC                              │
└─────────────────────────────────────────────┘
```

The critical insight: **layers 2 and 3 are shared by all filter classes**.
Only layer 1 (the writer) differs between LP, Phaser, Vocal, Morph
Designer, etc. The import strategy is to capture the writer's OUTPUT
(the packed corner words) and feed them directly into our identical
layers 2+3.

## 2. The three class kinds

The 23 menu entries fall into three architectural categories:

### 2.1 ROM table classes (17 filters)

Fixed writers that index into a ROM lookup table. The table stores
prototype stage words; the writer replicates them to the required
pole count.

```
MORPH ──→ ROM table lookup ──→ prototype stage words
                                    │
Q     ──→ (second lookup axis)      │
                                    ↓
                            replicate N times
                                    │
                                    ↓
                            corner bank (4 × N × 5 u16)
```

Classes: 2/4/6 Pole Lowpass, 2/4 Pole Highpass, 2/4 Pole Bandpass,
Contrary Bandpass, Swept EQ 1/2/3 Octave, Phaser 1/2, Bat Phaser,
Flanger Lite, Vocal Ah-Ay-Ee, Vocal Oo-Ah.

### 2.2 Generated classes (4 filters)

Writers that use a shared helper (`FUN_1802c59b0`) with different
support tables. These are "morphing EQ" classes — the Q axis carries
a second spectral shape rather than resonance.

```
MORPH ──→ profile table select ──→ stage words (slots 2/3/4)
                                    +
Q     ──→ expression table ──→ stage words (slots 0/1)
                                    │
                                    ↓
                            corner bank
```

| Class | Writer | Helper | Vtable | filter_id |
|---|---|---|---|---|
| `CPhantomMorph1` (Dual EQ Morph) | `FUN_1802c5d60` | `FUN_1802c59b0` | `0x1806d60b8` | `0x60` |
| `CPhantomMorphLP` (Dual EQ + LP) | `FUN_1802c5e40` | `FUN_1802c59b0` | `0x1806d60d8` | `0x61` |
| `CPhantomMorphLPX` (Expression) | `FUN_1802c5f10` | `FUN_1802c59b0` | `0x1806d60f8` | `0x62` |
| `CPhantomMorph2` (Peak/Shelf) | `FUN_1802c6020` | (independent) | `0x1806d6118` | `0x68` |

**Key trait**: these classes have no runtime blocks in
`ref/x3_menu/runtime_blocks/`. The extraction script did not (or could
not) snapshot their output. They must be regenerated by reimplementing
the writer logic — or captured from a running X3.

The helper `FUN_1802c59b0` writes a fixed three-row structure and
duplicates both endpoints across the Q axis. This means these classes
have **dead Q** by construction — the Q wheel does not change the
coefficients.

### 2.3 Morph Designer (1 filter + user presets)

A compiler that reads 6 records of `(type, freqA, gainA, freqB, gainB)`
and produces packed corner words via the type 1–3 grammar.

```
user XML/bytes ──→ Morph Designer compiler (FUN_1802c6590)
                        │
                        ↓
                  type 1/2/3 grammar (per-stage)
                        │
                        ↓
                  corner bank (6 stages, Q-collapsed)
```

**Key traits**:
- Only types 1–3 compile; type 0 and >3 are skipped
- Q axis is collapsed: endpoint A → slots at `+0x2c0`/`+0x338`;
  endpoint B → slots at `+0x2fc`/`+0x374`
- If ≥4 valid rows compile, forced to 6 rows, padded with bypass sentinel
- The grammar formulas are fully documented in
  `ref/ghidra_extracts/morphdesigner_types.md`
- The ~105 `x3_shape_*.body240` files are Morph Designer user presets

## 3. Runtime interpolation (shared)

`FUN_1802c3d40` — called for every filter instance, every parameter update.

```text
Input:  morph ∈ [0, 1]   (clamped)
        q     ∈ [0, 1]   (clamped)
        corner bank: 4 × 6 stages × 5 u16 words

Algorithm:
  For each stage si, for each word wi:
    edge0 = lerp_u16(corner[M0Q0][si][wi], corner[M100Q0][si][wi], morph)
    edge1 = lerp_u16(corner[M0Q100][si][wi], corner[M100Q100][si][wi], morph)
    result[si][wi] = lerp_u16(edge0, edge1, q)

  Each intermediate leg is truncated (i16 cast) before the next leg.
```

This is **identical** to TRENCH's `PackedCorners::interpolate_words()` in
`trench-core/src/minifloat.rs:147-161`. The `lerp_u16` function matches
(`diff as i32 as i16` truncation behaviour).

**Evidence**: `x3_groundtruth::interpolate_words_is_the_exact_source_of_decoded_interpolation`
test in `minifloat.rs` — interpolated words → kernel matches decoded
interpolation exactly.

## 4. Runtime decode (shared)

`FUN_1802c3600` — called after interpolation, before the cascade.

```text
Input:  6 stages × 5 u16 words (interpolated)

For each stage:
  d0 = decode(w0)     // minifloat → f64
  d1 = decode(w1)
  d2 = decode(w2)
  d3 = decode(w3)
  d4 = decode(w4)

  // Sentinels:
  //   decode(0x0000) = 0.0
  //   decode(0xffff) = 1.0

  // Recombination (kernel space):
  c0 = 4.0 * d0 + d1    // numerator curvature
  c1 = d1                // numerator linear term
  c2 = 4.0 * d2 + d3    // denominator curvature
  c3 = d3                // denominator linear term
  c4 = runtime_scale * d4  // gain, runtime_scale = 4.0

  // Biquad conversion:
  b0 = c4
  b1 = (c0 - 2.0) * c4
  b2 = (1.0 - c1) * c4
  a1 = c2 - 2.0
  a2 = 1.0 - c3
```

This is **identical** to TRENCH's `stage_words_to_kernel()` +
`kernel_to_biquad()` in `trench-core/src/minifloat.rs`.

`runtime_scale` is initialised to `4.0` by `FUN_1802c0150` at object
offset `+0x2a8`. TRENCH uses the constant `COMBINE_K = 4.0`.

## 5. AGC (shared)

`FUN_1802c04e0` — post-cascade level control.

- 16-float table copied by `FUN_1802bfa10`
- Sample-rate dependent: ≤65k → linear, 65k–130k → sqrt, >130k → sqrt(sqrt)
- Running multiplier at `this+0x08`
- Index wraps with `& 0x0f` (no clamp)
- Below 1.0: multiply samples. Otherwise: reset to 1.0
- Stereo: larger channel magnitude drives one shared gain update

## 6. Complete dataflow diagram

```text

                          │
          ┌───────────────┼───────────────┐
          │               │               │
     ROM TABLE       GENERATED        MORPH DESIGNER
      CLASSES         CLASSES          (user presets)
          │               │               │
          ▼               ▼               ▼
    Writer function  Writer function  Type 1-3 compiler
    (FUN_1802c4b80   (FUN_1802c5d60   (FUN_1802c6590)
     etc.)            etc.)            reads XML bytes
          │               │               │
          ▼               ▼               ▼
    ┌─────────────────────────────────────────┐
    │         CORNER BANK                      │
    │  4 corners × N stages × 5 u16 words     │
    │  (N=1..3, padded to 6 with sentinel)    │
    │  Stored at object + runtime offsets      │
    └─────────────────────────────────────────┘
                          │
          ┌───────────────┤
          ▼               ▼

          │               │
          └───────┬───────┘
                  ▼
    ┌─────────────────────────────────────────┐
    │    BILINEAR INTERPOLATION                │
    │    FUN_1802c3d40                         │
    │    lerp_u16 in packed word space         │
    │    → 6 stages × 5 u16 words              │
    └─────────────────────────────────────────┘
                  │
                  ▼
    ┌─────────────────────────────────────────┐
    │    MINIFLOAT DECODE + RECOMBINE          │
    │    FUN_1802c3600                         │
    │    u16 → f64 → kernel → biquad           │
    │    → 6 stages × 5 f64 coefficients       │
    └─────────────────────────────────────────┘

                  ▼
    ┌─────────────────────────────────────────┐

                  ▼
    ┌─────────────────────────────────────────┐

    │    Running gain, 16-float table           │
    │    → level-adjusted sample                │
    └─────────────────────────────────────────┘
```

## 7. The dataflow for TRENCH import

The import strategy is to **capture the corner bank** (writer output)
and feed it directly into TRENCH's interpolation + decode + cascade
— bypassing the writer entirely.

### 7.1 Fixed-class path (proven)

```text
ROM table bytes (DLL)
  → extract per-rate segment (extraction script, MISSING)
  → replicate to output_stages (extraction script, MISSING)
  → write runtime_blocks/*.raw (EXISTS in ref/x3_menu/)
  → pack as body240 (x3_fundamentals_to_bodies.py, EXISTS)
  → feed to TRENCH engine via PackedCorners (WORKS)
```

### 7.2 Generated class path (writer reimplementation needed)

```text
Support tables + control logic
  → reimplement writer function
  → produce corner bank
  → pack as body240
```

These classes have NO runtime blocks — only the raw support tables.
The writer functions must be reimplemented from Ghidra disassembly.

### 7.3 Morph Designer path (grammar known, XML corpus available)

```text
Morph Designer XML preset bytes
  → reimplement type 1-3 grammar (documented in morphdesigner_types.md)
  → produce corner bank (6 stages, Q-collapsed)
  → pack as body240
```

The grammar formulas are fully documented. The XML corpus exists
externally (71 presets, referenced in NEXT_TASK.md line 109).

## 8. What the existing `x3_fundamentals_to_bodies.py` does

1. Reads 44100 Hz runtime blocks from `ref/x3_menu/runtime_blocks/`
2. Parses 4 corners × N stages × 5 u16 words
3. Identity-pads to 6 stages
4. Packs as 240-byte body (`struct.pack` little-endian u16)
5. Codec-null: probes TRENCH engine at each corner vs df2 reference
   decode (worst-case difference reported)
6. Certifies through TRENCH's `certify()` (stability gate)
7. Writes `bodies/candidates/X3F_{name}.body240` if null < 0.01 dB
   AND stability certified

**What it does NOT do**:
- Handle sample rates other than 44100 Hz
- Handle generated classes (no runtime blocks exist)
- Handle Morph Designer presets (separate pipeline)
- Verify against real X3 hardware output
